# Winning Strategy — Lazarus for Kiroween 2026

**Goal:** Win Overall 1st Place ($30,000) + Resurrection Category ($5,000) + Bonus Prizes.

---

## 1. Category Choice: Resurrection

Why Resurrection over Frankenstein / Skeleton Crew / Costume Contest?

- **Clear narrative:** "Dead code comes back to life" fits the Halloween theme perfectly — memorable for judges.
- **Real impact:** Millions of abandoned repos solve real problems; judges score "Potential Impact" highly.
- **Kiro showcase:** Every Kiro feature has a natural home: Crew (agents), specs (resurrection plan), hooks (test + PR gates), steering (guardrails), MCP (GitHub read/write), PBT (mortician classification).
- **Demoable:** Before/after health score + live PR is a 3-minute demo dream.
- **Design:** Gothic UI doubles as "haunted interface" — could cross-pollinate Costume Contest voting even though we're in Resurrection.

## 2. Judging Criteria — How We Win Each

| Criterion | Our Tactic |
|-----------|------------|
| **Potential Impact** | Real problem (abandoned repos), measurable before/after health score, open-source output anyone can use. |
| **Technological Implementation** | Deep Kiro usage: Crew agents, spec-driven dev, hooks, steering, MCP, PBT. Document every feature in the write-up. |
| **Design** | Gothic-polished UI (dark theme, serif headings, accent color), WCAG AA contrast, keyboard nav, mobile responsive. |
| **Innovation/Idea** | Multi-agent resurrection pipeline is novel; spec-driven agent communication (files, not prompts) is unusual. |

## 3. Kiro Write-Up — The Hidden Scorecard

Judges must understand **how effectively you used Kiro**. We cover every prompt from the rules:

- **Kiro IDE / CLI / Web / Crew:** Primary dev in IDE, crew orchestration, Web preview — state which was used for what.
- **Custom agents:** Archivist, Mortician, Surgeon, Embalmer — roles, inputs, outputs, impact.
- **Agent hooks:** pre-resurrection, post-spec, pr-creation — what they automated and how they improved the process.
- **Spec-driven development:** spec first, then implementation; contrast with vibe coding.
- **Steering docs:** `kiro-crew-steering.md` + `code-style.md`; strategy that made the biggest difference (no full-framework rewrites).
- **MCP:** GitHub MCP (read repos, open PRs) + Filesystem MCP (specs/artifacts).
- **PBT:** Hypothesis-based dead-vs-active classification — issues caught that unit tests missed.
- **Kiro powers:** Python/FastAPI best practices, frontend accessibility.
